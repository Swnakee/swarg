# Module agent (`App/internal/agent`)

Purpose: domain core. Runs queued user messages one at a time against a `Provider` as a Turn: a loop of
model steps and tool batches. Keeps the history and the context meter, and reports everything through `Deps.OnEvent`. Imports only `chat`.

API:
- `Provider` - `Stream(ctx, chat.Request) (<-chan chat.StreamEvent, error)`; defined here, implemented elsewhere.
- `New(Deps) *Agent` - `Deps{Source, Provider, SystemPrompt, Model, MaxTokens, ContextLimit, Extra, ThinkExtra, ThinkTokens, OnEvent, Tools, Approve, Health, MaxSteps, Store, Trace, AutoCompact, LimitFor, Tasks, Now}`. `Source` is the name of the first Source (the config's provider, "" is fine); `Provider, Model, MaxTokens, ContextLimit, Extra, ThinkExtra, ThinkTokens, LimitFor, Health` form it (`a.src`).
- `Source{Name, Provider, Model, MaxTokens, ContextLimit, Extra, ThinkExtra, ThinkTokens, LimitFor, Health}` and `SetSource(s) error` (T11, R-100, I-36): the model server of every request built from now on (next Step, next Turn, summaries, the server check); a request in flight keeps its Provider (`stream` takes `a.src.Provider` under `mu` with the request). Blank name or nil Provider -> `ErrBadSource`, blank model -> `ErrBlankModel`. Records `Store.Provider(name)` then `Store.Model(model)`, trace `provider`, re-reads the limit (`limitFor` now reads `a.src`), and when the history estimate exceeds the new limit (and a WorkSpan exists) queues a Compaction at the HEAD of the queue; emits `EvProvider{Text: name}`, `EvModel`, `EvMeter`. `Source()` returns a copy. `Now` nil = `time.Now` (times the Generation speed). `ContextLimit` 0 turns the emergency batch off. `LimitFor func(model) int` nil = `ContextLimit` for every model (R-41). `Tasks TaskLimits{MaxDepth, MaxSteps, MaxPerTurn}`: `MaxDepth` 0 = no Tasks; `MaxSteps` 0 = 15, `MaxPerTurn` 0 = 8.
- `ToolRunner{Specs, Kind, Detachable, Label, Run(ctx, call, ToolHooks)}`, `ToolHooks{Progress func(chunk), Detach <-chan struct{}}` and `Approval{Allow, Note}` - tool side, implemented in `cmd/swarg`. `Tools` nil = one step, no `Tools` in the request. `Approve` nil = allow; `Background() bool` closes the detach channel of the running detachable mutating call (registered only after approval, cleared when `Run` returns; true once, false when none/idle/awaiting approval); `Health` nil = skip; `MaxSteps` 0 = 25.
- `Start(ctx)` - starts the single worker; cancelling ctx stops it and unblocks `Wait`. The worker checks ctx before every queue item, so queued texts, Loads and Compactions are dropped, not run, after the cancel (a steady feed of control items could otherwise keep it alive for ever).
- `Submit(text)` - queue a message; blank text ignored; never interrupts.
- `SubmitTask(goal) error` - queue a /task Turn: the goal runs as a Task first, then the Session model answers from the TaskResult; `ErrTasksOff` when Tasks are off; blank ignored. Like a text it waits for a running Turn, but it is never injected into one (see Task mode below).
- Unknown tool names (R-90, `similarTools`): the error result lists up to three offered tools that share a word with the called name (`unknown tool save_tool; did you mean mcp__demo__save?`); no shared word keeps the plain `unknown tool x`.
- `SubmitSkill(name, text string) error` (R-83): queues a /skill Turn: the user text (or "Apply this skill." when blank) is followed by a synthetic `skill` ToolCall `{"name": name}` run like a model's (`runPrelude`, shared with the /task goal), then the model answers. `ErrNoSkills` when the ToolRunner has no `skill` Tool. Like a goal it never joins a running Turn.
- `Interrupt()` - first press: stop output (drain), cancel tools; second press while interrupted = `Abort()`; no-op when idle; queue kept.
- `Abort()` - cancel the request (no drain) and tools; then `Health` runs in its own goroutine; no-op when idle.
- `Clear() error` - empty history, reset meter; `ErrBusy` while a turn runs; queue kept.
- `Load(history, ...LoadOption) error` - a resumed Session (see Persistence below); `WithMaxSeq(n)`; `ErrStopped`.
- `Compact(ctx) error` - queue a Compaction (see Compaction below); `ErrStopped` after shutdown.
- `Store` and `Trace` - nil-safe consumer interfaces (see Persistence below).
- `History() []chat.Message` - copy. `Busy()` - running or queue non-empty. `Wait()` - until idle and queue empty.
- `Event{Kind,...}` with `EvTurnStarted|EvDelta|EvActivity|EvProgress|EvDraining|EvTurnEnded|EvMeter|EvWarning|EvQueue|EvUserText|EvToolStart|EvToolOutput|EvToolEnd|EvModel|EvProvider|EvSpeed|EvTaskStarted|EvTaskEnded` (`EvActivity`: `Text` = a reasoning or tool-call-arguments chunk, counted by the UI, never shown, R-61; `EvModel`: `Text` = the new model id; `EvProvider`: `Text` = the Source name (SetSource); `EvSpeed`: `Speed` tok/s; `EvToolOutput`: `Call` + `Text` chunk, display only, never stored in history; `Call`, `Label`, `Brief`, `Output`; `Err` set for tool errors; `EvTaskStarted`: `Task` id, `Depth`, `Text` goal, `Call`; `EvTaskEnded`: `Task`, `Brief` = line 1 of the TaskResult, `Output` = the whole result). `Event.Task` names the Task whose loop emitted a Delta/Progress/Draining/Tool*/Meter/Speed event; "" = the Session.
- `FormatMeter(used, limit, est) string` - the only meter formatter (`35% · 5.6k/16k`, `~35% · ~5.6k/16k`).
- Telemetry on `EvMeter`: `CachePct`/`HasCache` (cached/prompt of the LAST usage report, clamped 0..100, kept across error turns, reset by `Clear`) and `Breakdown{System, User, Answers, CallArgs, ResultsFull, Stubs}` (estimated tokens of the next request; `System` includes tool schemas; the parts sum exactly to `chat.EstimateBytes` of the whole text, rounding is carried part to part). `FormatCache(pct, known)` -> `cache 80%` / `cache –`. `estimateRequest(chat.Request) Breakdown` is pure and stub-aware: a tool message with `Stub` set counts under `Stubs` (its `Stub` text), else under `ResultsFull`. The meter's estimate (`used` before any usage) is now `estimateRequest(a.request(system)).Total()`, so it includes tool schemas and stubs.
- `ToolStubber{Stub(call, output, brief) string; Touched(call) string}` (stub_iface.go) - OPTIONAL interface of a `ToolRunner` (type assertion; `ToolRunner` itself is unchanged). `cmd/swarg` `toolRunner` implements it by forwarding to `tools.Set`; `Touched` makes absolute paths project-relative. The agent loop calls it in the three batches below.

Invariants:
- One worker; `mu` guards queue, running, interrupted, stopped, the embedded `conversation` of the Session (history, system prompt copy, meter, cancel funcs, detach) and the Chain. A Task's loop runs in the goroutine of its `task` call while the worker waits in `runBatch`, so Provider requests still never overlap (I-1).
- `OnEvent` is never called under `mu`; it may call `Busy`, `History`, `Interrupt`, `Clear`.
- Dequeue sets `running`, clears `interrupted` and appends the user message in one critical section.
- Interrupt: the worker emits `EvDraining` once, discards further deltas, keeps reading until
  `EventDone`; the request is never cancelled; only text delivered before the interrupt is stored
  (`Interrupted`, nothing if empty). The next queued item starts after the drain.
- Errors and empty answers store the user message only; consecutive user messages are merged
  (blank-line join) when building a request, history is unchanged.
- Meter: exact `Prompt+Completion` of the last usage, kept across error turns; estimate before
  any usage and after `Clear`. Warnings at 80% and 100% fire once per upward crossing.
- Turn start: `TurnStarted`, then a Meter event with the estimate of the first request (the panel shows the context use during the first Turn too; found in the T3 final regression).
- Events per turn end: optional `Warning("empty answer")` / denial note, `Meter`, meter warnings, then `TurnEnded` ALWAYS LAST (plain mode stops reading at it).

Task mode (files `conversation.go`, `task.go`; Domain R-37..R-40, I-12..I-14):
- `conversation` is the history the Step loop works on: the Session (depth 0, embedded in `Agent`) or a Task (depth >= 1). `runTurn` is the Turn wrapper (events, `endTurn`, Health); `runLoop(c, repeats)` is the Step loop on any conversation. Per conversation: `ctx` (the Turn's ROOT ctx: requests derive from it, so a soft Esc drains instead of disconnecting), `toolsCtx/toolsCancel`, `reqCancel`, `detach`, history, system, meter, emergency flag, stub batch, `lastReqSeq`, depth, id (`t1`, `t2`, ...), goal. `Agent.chain` is the running Chain (Session first); `Interrupt` cancels every level's tools, `Abort` the innermost request too; `Background` uses the innermost detach.
- The `task` Tool (`taskSpec`, name `task`, one argument `goal`) is appended to the Tools' specs while `depth < MaxDepth`; `TaskBlock` is its SystemPrompt line (main adds it as `tool-task`). `exec` dispatches a `task` call to `runTask` after the bad-args check and the R-10 skip (at depth 0 a `task` call is skipped while text is queued, like a mutating call) and before `Tools.Kind`. Guards, each an error ToolResult without a model request: empty goal, `depth >= MaxDepth`, `turnTasks >= MaxPerTurn` (counted over the Chain of one Turn, reset in `dequeue`), a goal equal (trimmed, case-folded, blanks collapsed) to a running ancestor's goal or to the Turn's own text (not for the synthetic call of `/task`).
- The child conversation: the same SystemPrompt text, the parent's limit, its own `toolsCtx` from the root ctx, pushed on the Chain (cancelled at once if the Turn is already interrupted); its first Message is the goal in the frame `Sub-task: <goal>\nDo only this. Do not ask the user. When done, answer with a short report: ...` (`taskFrame`). Inside: Steps, tools, Approval (the denial note says "report it in your result"), the emergency stub batch (in memory), the loop and repeat guards, `Tasks.MaxSteps`. No `inject` (queued text waits for the Session), no Compaction. Child Messages never reach the Store (`appendLocked` stores at depth 0 only; `flushBatchLocked` patches likewise); the Trace gets every record tagged `task: <id>` (`traceC`) plus `task_start{id, parent, depth, goal}` and `task_end{id, status, steps, result}`.
- TaskResult (`taskResult`): line 1 = `<status>[; files: a, b]` (status from `turnResult.status`: `done`, `stopped: step limit`, `stopped: tool calls were denied`, `stopped: answer cut off` (FinishLength), a guard's `stopped: ...`, `failed: <error>`, `interrupted`, `aborted`; files = `ToolStubber.Touched` of the child's successful edit/write calls plus the `files:` of nested TaskResults, deduplicated), then the report (the final text `headTail` 750+750 bytes, else `generatedList` of the child's history clipped to 1500), then `steps: N/M`. Line 1 is the ToolResult's `Brief`, so a Compaction keeps it. `failed:` returns an error result (`error: ` prefix, `Failed`, R-7); a denial stop sets `denied` (one denial for the parent). The parent's loop ends its own level right after `runCalls` when the Turn is interrupted, so the Chain unwinds innermost first.
- `/task` (`SubmitTask`, `runGoal`): the queue item carries `task: true`; `leadingTextsLocked` stops at it (never injected); `runTurn` first appends an assistant Message with one synthetic `task` call (`call_<n>`) and runs it through `runCalls`, then enters the loop at step 1.
- The TaskResult is never stubbed: `tools.Set.Stub` knows no `task`, so `candidates` finds no stub text; the report stays in the history until a Compaction folds the span to its generated list (line 1 survives there).

Turn loop (files `turn.go`, `tools.go`):
- Step = one model request. Text-only answer ends the Turn (queued text then starts a NEW Turn).
  With tool calls: store assistant (empty text allowed), run the calls, append one tool message per
  call in call order, then inject queued user texts (`EvUserText`, `EvQueue{0}`, one `mu` section)
  and send the next request. After `MaxSteps` steps: `Warning("step limit reached (N)")`.
- Unparsed tool call (F10 of the model comparison): a Step that ends with `finish: tool_calls` but no call means the server could not parse the model's call (mlx logs `Failed to parse tool call`). The loop does not end silently: the first time per loop (Session or Task) and below the step limit it emits `Warning("the model's tool call could not be parsed; asking it to call again")`, appends a user Message `unparsedNudge` ("Your last tool call could not be parsed. Call the tool again with valid JSON arguments."; stored, so a resumed Session shows it as a user line) and sends the next request; a second such Step ends the loop with the note `stopped: the model's tool call could not be parsed`.
- Undelivered output (F11, `lostCall`): a Step with `finish: length` and no text, no reasoning and no call (not cut by the loop guard) means the server held a too long or endless tool call back until `max_tokens` and could not parse it, so nothing reached swarg. Same path as F10, sharing its one nudge per loop: `Warning("the model's output was not delivered (probably a tool call that was too long or unparsable); asking it again")`, the stored user Message `undeliveredNudge` formatted with the request's `max_tokens` (`turnResult.limit`: the output limit of N tokens, write a long file in parts with `write_file` and then `"append": true`, R-67), next request; a second lost Step (either kind) ends the loop with its stop note (`stopped: the model's output was not delivered`). A reasoning-only cut stays a plain cut. Live origin: Qwen3.5-2B asked to write a phrase 200 times on one line (T4 cross-model test, `loop`).
- Dropped answer (T5 M1, `lostCall`): a Step with `finish: stop`, more than one completion token (usage) and no text, no reasoning and no call means the server dropped what the model wrote (mlx_lm.server 0.31.3 discards a tool call the model did not close with `</tool_call>`). Same nudge path, one per loop: `Warning(droppedWarning)`, the user Message `droppedNudge` (send it again, complete), next request; a second lost Step ends the loop with `stopped: the model's answer arrived empty` (the plain "empty answer" warning is skipped when a stop note is shown). Without usage from the server (tokens 0) the case is off. One token (the end token only) is a real empty answer: no nudge. Live origin: Qwen3.5-9B on eval edit-02 (3/3 runs).
- Denials: a step with at least one denied call, when the Turn's denials total 2 or more, ends the Turn
  after the tool messages are appended: no further request, `Warning("stopped: tool calls were denied")`,
  `TurnEnded` with `FinishStop`. One denial alone lets the model answer.
- Schedule: consecutive read-only calls run in parallel, every other call alone, in order. Mutating
  calls not yet started are skipped when text is queued. Confirm-needing calls go through `Approve`.
- Repeat guard (`repeatguard.go`, R-24): per Turn, consecutive calls with the same tool, canonical args (key order/spacing ignored) and the same outcome (the same error text, or for a success the same output) count as a streak; a denial, a different call or a different outcome resets it, and so does a success of a polling Tool (`pollTools`: `shell_output`, waiting on a job is normal). At 2 the ToolResult gets a note (history content only, not the ToolEnd event): failures `\n[this exact call failed 2 times in a row; ...]`, successes `\n[this exact call returned the same result 2 times in a row; ...]`; at 3 the Turn ends like a denial stop with `Warning("stopped: the same tool call kept failing")` or `"stopped: the same tool call kept returning the same result"`, `TurnEnded` with `FinishStop`. The owner's case: `find . -type d | wc -l` run 16 times with the same `1`. A batch is one decision (F12, `newStep` from `runCalls`): within one Step the same call with the same outcome counts once, for the streak and for the cycle window, so streaks and cycles grow only across Steps (the model saw the result in between); different calls of one Step still count in order. Live origin: KAT-Coder sent 5 identical `cat /etc/hostname` (and 10 ping/pong) in one Step and the old per-call count ended the Turn before the answer. Cycle rule (R-44): the guard also keeps the keys (tool + canonical args + outcome with `bg\d+` replaced by `bg#`) of the last 6 outcomes of the Turn, polling successes included; a denial clears them. When the list ends with the same pair of different keys 2 times (4 calls) the ToolResult gets `\n[these 2 calls keep repeating with the same results; ...]`, 3 times (6 calls) the Turn ends with `Warning("stopped: the same tool calls kept repeating")`. A pair does not count if both keys are polling successes (`shell_output` on one or two jobs). The origin: the 4B alternated `shell` ("sh slow.sh &") and `shell_output` 12 times (model comparison, shell-03).
- Result texts: `error: <text>`, `error: unknown tool <name>`, `denied by the user[: note]. Do not retry this or a similar action; ask the user how to proceed.`,
  `skipped: the user sent a new message`, `cancelled by the user`; `Run` panics are recovered.
- History validity: every assistant tool call has exactly one tool message; args are normalized
  before storing (blank/null -> `{}`, double-encoded string unwrapped once, else `{}` + error result;
  the server json-parses every stored value); missing/duplicate ids become `call_<n>` (session counter);
  calls of an interrupted/error stream are dropped; `FinishLength` with calls -> error results.
- Cancel: `toolsCancel` (per conversation: tools and `Approve`) is hit by the first Interrupt (every level of the Chain), `reqCancel`
  (per step, the innermost conversation) only by Abort. `ToolStart`/`ToolEnd` are emitted one at a time by the goroutine running the loop (the worker, or a `task` call's goroutine), never concurrently. `ToolOutput` comes from the tool goroutine via `ToolHooks.Progress`, serialized per call by a mutex and dropped after `Run` returned (so it is always between that call's Start and End), never under `mu`.

Context economy (files `economy.go`, `loopguard.go`; PLAN 5.1, Domain R-16..R-19, R-22):
- Bookkeeping: every history append goes through `appendLocked` (`Seq` monotonic for the Agent's life, never reset by `Clear`). The user Message that starts a Turn has `TurnStart`; queued texts injected mid-Turn have `Injected`; tool results store `Brief`, `Label` (from `runBatch`) and `Failed` (`res.err != nil`; denied/skipped/cancelled notes are NOT `Failed`).
- `request()` sends `Stub` as the wire content of a tool Message that has one, on a COPY (the copy keeps `Stub` set so `estimateRequest` counts it under `Stubs`). History `Content` never changes.
- Three batches, all under `mu`, each makes the meter fall back to the estimate (`hasExact=false`) when it changed something:
  - Turn end (`finishTurnLocked`, called by `endTurn` before the Meter event): every result of the finished Turn gets its Stub, then big arguments shrink.
  - Inject (`stubInjectLocked`, when queued texts are injected; an unavoidable cache miss anyway): the Turn's results get Stubs except the trailing tool Messages of the last Step (the model has not answered them yet) and reads that are not stale. A Meter event follows.
  - Emergency (`stubEmergencyLocked`, `emergencyBatch` before every Step, at most once per Turn, only when `ContextLimit > 0`): when the estimate of the next request is above 65% of the limit, stubs stale reads first, then the largest results, until the estimate is at or below 50%; never the last 2 tool Messages of the Turn, never a read that is not stale. If nothing qualifies the once-per-Turn flag stays unused. A Meter event follows.
- Which result may be stubbed (`candidates`): only a result that ran (`ran`: not `Failed`, not a denial/skip/cancel note) and has no Stub yet; the stub text is `ToolStubber.Stub` (a runner without `ToolStubber` or an empty Stub keeps the content) or, for a stale `read_file`, `[read_file <path>: stale, the file changed later]` / `[read_file <path>: stale, read again later]` (no length check: the stale note is always worth sending).
- Stale (`staleReason`, within the Turn): a successful `edit_file`/`write_file` later touched the same cleaned path (`ToolStubber.Touched`), or a later successful `read_file` of the same path covers the same or a larger line range (offset default 1, limit default 200 - mirrors `read_file`). Paths compare as given after `filepath.Clean` (case-sensitive). The tool names `read_file`, `edit_file`, `write_file` are constants in `economy.go`.
- Argument shrinking (`shrinkArgs`, Turn end only): `write_file.content`, `edit_file.old`/`new` longer than 1 KB become `(omitted from history: N lines, X.X KB; the file on disk has it)`. The new Args are re-encoded JSON (no HTML escaping, keys sorted); unparsable args are left alone. The `ToolCalls` slice is replaced, not edited, so a `History()` copy held elsewhere never changes.
- Loop guard (`loopGuard`, one per model Step, fed by the delta handler): a normalized completed line (digits, numbering, bullets, markdown and case removed; at least 8 runes) seen 4 times among the last 40 counted lines, or the last 300 runes already present twice before (not overlapping the tail), or the current unfinished line ending with 3 copies of one unit of 8..400 bytes over at least 160 bytes (the period rule: a phrase repeating inside one long line; not inside a fence, not for a run of one or two symbols such as a `────` ruler) cancels the request (the handler ends the read, `stream`'s deferred `reqCancel` disconnects, then `Health` runs like after an Abort), stores the answer cut before the second copy with `Truncated` and warns `stopped: the answer started repeating itself`; `TurnEnded` has `FinishStop` (not `length`: the UI would add a false "cut off by a limit" notice), ToolCalls of the cut request are still marked cut. Lines inside a ``` fence are not counted by the line rule (repeated code lines such as `if err != nil {` are normal); the tail rule still sees them. Interrupted/drained text is never fed to the guard.

Spend (`spend.go`; Domain R-111, R-114, I-39):
- `Spend() Spend{Total, ByModel}` (a copy). `chat.Usage.Cost` of every `EventUsage` (Turn steps incl. Tasks, and Compaction summary requests in `ask`) goes through `addSpend(model, usd)`: per-model sum, `Store.Spend` (REQUIRED Store method, like Thinking), trace `spend`, `EvSpend{Spend: total}`, and one `EvWarning` when the total first reaches `Deps.WarnUSD` (> 0). The model is the one of the request (`turnResult.model`), not the current Model choice. A cost <= 0 is ignored.
- `WithSpend(byModel)` LoadOption installs the Session's spend (a resumed Session), emits `EvSpend`, and counts the warning as given when the loaded total is already >= `WarnUSD`; nothing is recorded (the SessionFile has it). Without the option a Load leaves the spend alone.
- `FormatUSD(v)`: `$0.0012` / `$0.457` / `$12.50`.

Thinking mode (`think.go"; Domain R-60, I-30):
- `Thinking() bool`; `SetThinking(on)` - the mode of every request built from now on: `request()` lays `Deps.ThinkExtra` over `Deps.Extra` (a new map, nested maps merged one level) and uses `Deps.ThinkTokens` when > 0. Same mode = nothing; else `Store.Thinking(on)`, trace `thinking`, `EvThinking` (`Text` "on"/"off"). `WithThinking(on)` LoadOption sets it without a Store record (the SessionFile has it) and emits `EvThinking` when it changed. `Store.Thinking` is a REQUIRED method: main's `swStore` and the test proxies must forward it (an optional interface silently dropped it in a wrapper).

Model choice (`model.go`; Domain R-30, I-9):
- `Model() string`; `SetModel(name) error` - trimmed; blank -> `ErrBlankModel`; the model in use -> nil, nothing recorded; else the model of every request built from now on (next Step of a running Turn, next Turn, Compaction summaries; main's `Health` reads `Model()`), `Store.Model(name)`, trace `model`, then `EvModel` (after unlock). Safe from any goroutine.
- The ContextLimit follows the model (R-41, I-13): `limitFor(model)` = `Deps.LimitFor`, else `ContextLimit`. `SetModel` and `Load`+`WithModel` call `setLimitLocked`: when the limit changes, `meter.limit` is set, the 80%/100% warnings re-armed, `hasExact` dropped, and an `EvMeter` follows `EvModel`. `stream` sets the conversation's `meter.limit` to the current model's before every request, so a Task started before a `/model` switch measures its next request against the new limit. `enqueueAutoLocked`, the emergency batch and the summary chunking (`a.limit()`, which locks) read the meter's limit, never `Deps.ContextLimit`.
- Gotchas: a change inside a Turn reaches the requests at once, but the SystemPrompt env block (`Model:` line, rewritten by main on `EvModel`) only from the next Turn (R-4).
- `WithModel(name)` LoadOption: Load also sets the model WITHOUT a Store record (the SessionFile has it) and emits `EvModel` after the Meter event when it changed; blank or the same = nothing.

Generation speed (`speed.go`; Domain R-29):
- `stepClock` per Step (in `turnResult`): `start` before `Provider.Stream`, then `note(ev, Now())` for every stream event in `handle` (first generated delta of any kind: non-empty text or non-empty reasoning; last progress; usage completion tokens; done). `speed()` = tokens / (done - from), from = that first delta, else last progress, else start; no speed without usage, with 0 tokens, without done, or with no time passed. R-43: reasoning tokens count in usage (a clock started at the first text inflated a thinking model's tok/s). A tool-call-only Step counts from the end of prompt reading: mlx_lm.server sends the whole tool call in one chunk at the END of the generation, so a clock started at that chunk gave 500-2000 tok/s in the T4 live check (fixed on `fix/toolcall-clock`); the understated value agent-1 saw on such Steps stays open (the server's last keepalive may precede the end of prefill).
- Truncated prompt (R-65): `stream` keeps `estimateRequest(req).Total()` in `turnResult.sent`; on `EventUsage` `meter.cut(prompt, sent)` returns the warning once per meter when the reported prompt tokens are under half of an estimate above `cutFloor` (2048), emitted as `EvWarning`; each conversation (Session, Task) has its own meter; `meter.reset` (Clear) re-arms it. Ollama reports the full prompt in `prompt_tokens` (cached tokens included), so a cache hit is not a false positive.
- Reasoning (R-42): `handle` collects `EventReasoning` into `turnResult.reasoning`; `commitLocked` stores it as `Message.Reasoning`; `request` sends it back for the assistant Messages after the last TurnStart only (the copy blanks earlier ones, so the estimate counts what is sent); `traceReply` records it. The loop guard is not fed with reasoning (a thinking loop is bounded by the server's max tokens).
- `reportSpeed` at the end of `stream` (before `prepare`, so before any ToolStart): skips aborted, looped (Loop guard) and error Steps; else trace `speed` {tokens, ms, tps} and `EvSpeed`. A drained (interrupted) Step still counts: the stream was read to its end. Compaction summary requests report no speed.

Persistence (files `store.go`, `load.go`, `trace.go`; PLAN 2.3b, 5.2, 5.4, Domain R-20, R-21, I-6, I-7):
- `Store{Message(m) error; Patch([]chat.Patch) error; Clear() error; Compact(fromSeq, toSeq, summary) error; Repair(ms) error; Model(name) error; Provider(name) error; Thinking(on) error; Spend(model, usd) error; Flush() error}` - `session.NewStore(writer)` satisfies it. Calls come right after each history change, in history order: every `appendLocked` (user text, assistant, each tool result in call order, injected text), one `Patch` per stub/arg-shrink batch (`flushBatchLocked`: Turn end, inject, emergency; `chat.Patch{Seq, Stub, Args}`), `Clear`, `Repair` (Load), and `Flush` LAST in `endTurn` (after the Patch). `Compact(fromSeq, toSeq, summary)` is called once per replaced WorkSpan. Messages passed to `Message` carry their `Seq`.
- `Trace{Record(kind string, v any)}` - `*trace.Writer` satisfies it; if it also has `Err() error` the first error is reported as one Warning. Records: `request` {step, msgs, added (messages appended since the previous request, in full, Stub as sent + `stub:true`), model, tools}, `delta` {text, calls, finish[, error]} once per reply, `usage` {prompt, completion, cached}, `tool_start` {id, name, args (raw, full), label}, `tool_end` {id, name, brief, output (what the model got), ms, capped[, error]}, `approval` {id, name, allow, note}, `interrupt`, `abort`, `stub_batch` {why: turn_end|inject|emergency, stubbed (seqs), shrunk (seqs)}, `loop_guard` {kept_bytes}, `warning` {text}, `error` {text, finish}, `load` {messages, repaired, seq}, `clear`, `task_start` {id, parent, depth, goal}, `task_end` {id, status, steps, result}; every record made by a Task's loop also carries `task: <id>`. `capped` is detected from the `[... N bytes cut;` note of `tools.Cap` (the agent never sees the uncut output).
- Mechanism: both are queued under `mu` as `outOp` (`storeLocked`, `traceLocked`) and performed by `drain` after unlocking, serialized by `storeMu` so queue order is call order; a Store or Trace may call `History`/`Busy`. `sync()` drains and emits the warnings; `endTurn` drains BEFORE `TurnEnded` so a storage Warning never follows it.
- I-7: the first Store error becomes ONE Warning (`the session is no longer saved: ...`) and the Store is not called again (a file with a hole would not replay) until the next Load: `applyLoadLocked` queues a rearm op, so the Store (possibly another SessionFile after an in-app switch) is tried again from the Load on (code review F3). A Trace error gives one Warning (`the trace is no longer written: ...`). Neither ever fails a Turn.
- `Load(history, opts...)` is a control item in the queue, executed by the worker between Turns (R-18): it never fails with `ErrBusy` - while a Turn runs it waits its turn; texts submitted before it that are queued during a running Turn still join that Turn (inject takes only the texts ahead of the first control item); texts submitted after it run after it. It returns at once; `Wait()` returns after it ran (the item leaves the queue last, after the Store and Trace calls); an `EvMeter` follows. It copies the input, numbers messages without `Seq` above the highest, restores `Seq` (max of the history and `WithMaxSeq`, which main passes from `session.Loaded.MaxSeq()` so numbering stays above ids of cleared or compacted messages) and the `call_<n>` counter, resets the meter and the stub batch state, appends a `cancelled by the user` result (Brief the same, no Label) at the END of the history for every ToolCall without a result (R-21) and records exactly those with `Store.Repair`. The loaded messages are not stored again. `ErrStopped` after the worker stopped.
- Wiring (main, later): `d.Store = session.NewStore(w)`, `d.Trace = traceWriter`; resume = `l, _ := session.Load(path)`, `w, _ := session.Open(path)`, `ag.Load(l.Messages(), agent.WithMaxSeq(l.MaxSeq()))`.

Compaction (files `compact.go`, `compact_spans.go`, `compact_summary.go`; PLAN 2.6, 5.2, 5.3, Domain R-16, R-18, R-23):
- `Compact(ctx)` enqueues a control item and returns at once; the worker runs it between Turns, in queue order (a running Turn finishes first, text submitted after it waits). `Busy()` stays true (the item leaves the queue last), `Clear` is `ErrBusy` while it runs. It never overlaps a model request (I-1): proved by `laneProvider` in tests.
- Spans (`findSpans`): maximal runs of assistant-with-ToolCalls plus their results. User Messages, any assistant Message without calls (final answers, interrupted/truncated text) and earlier WorkSummaries END a run, so they stay verbatim and an Injected user splits a Turn's work in two. A run whose calls and results do not pair up in order (a Load repair appends results at the END of history) or without `Seq` is skipped. All Turns are finished when the worker compacts, so the "current Turn" is never touched.
- Per span, oldest first: size = estimated tokens as sent (Stubs count as sent). Under 600 tokens: generated list `<tool> <label>: <brief>; ...`, no model call. Else a summary request (same Provider, Model, Extra; no tools; MaxTokens 300; system `summaryPrompt`; input = `Task:` user text 1000 bytes + steps `- <tool> <label>: <brief>` with result head/tail 500 bytes + `- note:` for the model's text between calls). If the input passes 50% of `ContextLimit` it is chunked and each chunk's summary leads the next chunk's input. Fallback to the generated list when the reply is empty, not shorter than the span, saves under 30%, or the request failed (that also marks the run failed and gives ONE warning `compaction: the summary request failed (...)`). A span is replaced only if the chosen text saves >= 30% (else it stays).
- Replacement: the span becomes one assistant Message `{Content: "[work summary] "+text, Summary: true, Seq: new}`, `Store.Compact(fromSeq, toSeq, summary)` and a Trace `compact` record {from_seq, to_seq, tokens, prompt, inputs, replies, fallback, why, summary, applied, gain, summary_seq} per span, then `hasExact=false`.
- Events: `EvCompactStarted{Spans, Before}` ... warnings ... `EvMeter` (estimate), `EvCompacted{Spans replaced, Before, After}` (estimated tokens of the next request). Every Started is followed by exactly one Compacted (Spans 0 when nothing was replaced or the user stopped it, then a `compaction stopped` warning). No spans at all: only the warning `nothing to compact`, no Started.
- Esc: the first `Interrupt` stops after the summary request in flight is read to its end (its reply is thrown away; spans already replaced stay); a second `Interrupt` or `Abort` disconnects the request (and runs `Health`). Usage of summary requests never reaches the meter.
- Auto: `enqueueAutoLocked`, called by the worker at every Turn end under the same lock that clears `running` (so `Wait` covers it), puts an automatic item at the HEAD of the queue (before queued texts) when `AutoCompact` > 0, the meter value (exact or estimate) >= AutoCompact% of `ContextLimit`, a span exists and the head is not already a control item. Circuit breaker: a run that failed (summary request error) or replaced nothing counts; the second in a row sets `autoOff` and warns `auto-compaction is off: context still full: use /clear`; a manual Compaction that replaced something without failing re-arms it; a run stopped by the user counts for nothing.
- Qwen chat template check (two consecutive assistant Messages: summary, final answer) is e2e only.

Gotchas:
- `Clear()` and `Load()` queue the Store/Trace records like any change; `Clear` still returns `ErrBusy` while a Turn runs.
- A history comparison in a test must drop the bookkeeping fields (`plain` in `bookkeeping_test.go`); request copies still carry `Seq`/`TurnStart` etc. (they are never sent to the API).
- `ToolStubber.Stub` and `Touched` run under `mu`; implementations must be pure and fast.
- `Queue` events from `Submit` and from the worker are emitted outside the lock, so a stale
  count can arrive out of order when a Submit races a dequeue.
- An `Interrupt` that arrives after the final `EventDone` was read is ignored for that turn.

## Sub-agents (T13 C, R-120..R-127, I-41, I-42)

Files: `subagents.go` (types, `runAgent`, progress), `agentlimit.go` (`slots`), `pathlock.go` (`pathLocks`).

- `Deps.Agents AgentDeps{Types, Open, Slots, Max}`: `Types() []AgentType` = the types on offer now (none = the `agent` Tool is not offered; main returns none under the compact profile); `Open(AgentType) (AgentRun{Source, System}, error)` resolves the run's Source and system prompt (main builds both); `Slots(source) int` = requests at once on a Source; `Max` = agents at once overall (0 or > 4 = 4). A nil `Types` or `Open` = no agents.
- `AgentType{Name, Description, Tools, MaxSteps, Server, Model, Profile, Body}`; `Allows(name, readOnly)`: `Tools` entries are names, `*` and `readonly`; empty = all.
- Tool `agent {type, goal}` (`agentSpec`, type names as an enum): offered by `specs` only at depth 0 and only when `Types()` is not empty; an agent's `specs` are the runner's specs filtered by `Allows`, never `task` or `agent`; `exec` refuses a call outside the allowlist and treats `task`/`agent` inside an agent as unknown tools.
- `runAgent`: checks (empty goal, unknown type, interrupted, per-Turn cap shared with Tasks, same goal already running), `Open`, a child `conversation` (`agent *agentRun` holds type, Source and the parent's call; `maxSteps`; `step`), registered in `Agent.agents` (NOT on the Chain: siblings run at once; `toolCancelsLocked` and `Abort` walk it), then waits for a Slot (Source first, then global; a waiting agent holds nothing) and runs `runLoop`; the result is `taskResult` (R-38).
- `parallel(c, p)` counts an `agent` call as parallel, so one step's agent calls share a batch (`runBatch`).
- Per-conversation Source: `srcOf(c)`/`limitOf(c)` pick the agent's Source and model for `request`, `stream` and `emergencyBatch`; thinking (R-60) applies to the Session only.
- Events: `emit` routes events whose `Task` id starts with `a` to `agentEvent`, which turns a ToolStart into a live line `step N/M <label>` (and `runAgent` adds `model <id>`, `waiting for a free slot on <source>`) as `EvToolOutput` of the parent `agent` call; nothing else of an agent reaches `OnEvent` (I-42). Spend is untagged and adds up.
- Approvals: an agent's `Approve` goes through `agentApproval` (a 1-slot semaphore, ctx-aware) so prompts queue.
- File lock: `exec` takes `pathLocks.lock(Touched(call), who)` around the Run of every mutating call with a Touched path; busy = error ToolResult naming the holder. Only file tools report a Touched path; `shell` can still write anything.
- Race notes: `prepare` takes `mu` for `callSeq` (agents prepare calls concurrently); `agents`, `agentSeq`, `turnTasks` are guarded by `mu`; an agent has no Detach (the Esc/Background path is the Chain's).
- Gotchas: an Esc that arrives before an agent is registered cancels the call unstarted (`cancelled by the user`) instead of `interrupted`; `Types()` runs under `mu` (in `specs`) so it must not call back into the Agent.
