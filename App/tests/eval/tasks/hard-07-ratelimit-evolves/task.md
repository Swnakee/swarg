Build a token-bucket rate limiter over three turns as requirements change; earlier work must be adapted, not discarded.
In ratelimit.py, implement the class TokenBucket(capacity, rate, clock=time.monotonic). It starts full; `rate` is tokens added per second; the token count never goes above capacity. `allow(cost=1)` takes `cost` tokens and returns True if there were enough, otherwise returns False and takes nothing. Also add a read-only property `tokens` that shows the current count after refilling. The clock is an injectable function returning seconds, so tests can fake it. Add a few tests to tests/test_ratelimit.py and run them.

Requirements changed. Two things: (1) a request whose cost is bigger than the capacity can never succeed, so allow() must return False for it and must NOT drain the bucket (this applies to TokenBucket too). (2) We need limits per client, so add a class Limiter(capacity, rate, clock=time.monotonic) with `allow(key, cost=1)` that keeps one bucket per key (a new key starts full), `retry_after(key, cost=1)` returning how many seconds until a request of that cost would be allowed (0 if it would be allowed now, `float("inf")` if it can never be allowed; it must not consume anything), and `len(limiter)` giving the number of keys currently tracked. A key is dropped from tracking as soon as its bucket has refilled to full capacity (a full bucket is the same as a new key); check this on every call to allow, retry_after and len. Keep TokenBucket working as before. Update the tests.

Two more things. (1) The clock may jump backwards (it happens on our servers). When it does, no tokens are added for that call and the reference time moves back to the new reading, so later forward movement is counted from there; this must never raise or produce negative tokens. Apply it to both classes. (2) Limiter state must survive restarts: add `dump()` returning a JSON-serializable dict with the full state (including capacity and rate, keys are strings), and a classmethod `Limiter.load(state, clock=time.monotonic)` that rebuilds it. The new process has a completely different clock, so store the time elapsed since each bucket's last update, not absolute times; the time between dump and load is not counted. A dumped-and-loaded limiter must behave exactly like the original did at the moment of the dump. Update the tests and run everything.
